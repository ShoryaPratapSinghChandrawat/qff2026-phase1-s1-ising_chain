## 2. V1 story (the only flow that must work end to end)
1. A buyer checks out in the demo store with PayPal Sandbox (or the mock checkout without credentials).
2. The order appears in MerchantShield.
3. A scan flags risk with plain-English reasons and lists MISSING EVIDENCE (no tracking number, no shipped date, no buyer communication logged...).
4. The agent proposes actions (add tracking, message the buyer, flag for review).
5. The merchant approves or rejects in the Action Inbox.
6. Execute: adds tracking to the PayPal order (LIVE when verified, else clearly SIMULATED/MOCK).
7. The audit log and a BEFORE/AFTER diff show exactly which fields changed.
Disputes (evidence packet, drafted response, approval, submission) are Phase 6. Refunds, accept-claim, webhooks and the PayPal Agent Toolkit/MCP are STRETCH only.

## 3. Honesty rules (hard)
- Every record has a source chip: LIVE (a real PayPal Sandbox response), SIMULATED (we generated it), MOCK (no credentials / fallback). Never imply a mock response is live.
- Demo membership is independent of source: is_demo (bool) + demo_run_id (nullable).
- Scores are ESTIMATES from a prototype trained on SYNTHETIC data. Never show "win probability", "chance to win", "money protected", "X% fewer disputes", or any unmeasured claim. The UI shows only MEASURED facts: fields changed, evidence found/missing, data source, actions approved/executed, and plain sums such as "order value flagged".
- Dispute scoring is a transparent evidence-strength CHECKLIST, not a prediction.
- LLM output may use only facts from our data. Reject and replace output that invents a tracking number, date, amount, identity or other material fact; record "hallucination_guard_triggered" in the audit log.
- Do not say an external action succeeded unless success was confirmed. An uncertain action stays UNKNOWN until reconciled.
- Never claim exactly-once semantics for external calls.

- Root files: LICENSE (MIT), README.md, DECISIONS.md, BUGS_FIXED.md, .gitignore, .env.example, PHASE, .nvmrc, scripts/. Never commit secrets, .env, .venv, node_modules, dist, *.db, caches or generated runtime files.

4.2 Timestamps
All timestamps are timezone-aware UTC and serialized with the "Z" suffix. Test it. No naive datetimes.
4.3 Demo mode
- Set DEMO_MODE explicitly in .env.example (true), any deployment config, and every test needing demo data. If unset, treat as false and log a clear startup warning.
- Seeding and POST /api/demo/* exist ONLY when DEMO_MODE=true (else /api/demo/* returns 404 and startup never seeds or deletes). Seed only when the DB is empty.
- Seeded records: is_demo=true, normally source=SIMULATED. Records from a real Sandbox response: is_demo=false, source=LIVE.
- POST /api/demo/reset deletes ONLY rows with is_demo=true AND source != LIVE, with dependent rows (messages, evidence, actions, related audit rows) in a foreign-key-safe order inside ONE transaction, then writes ONE kept audit row "demo_reset". It never deletes is_demo=false or LIVE rows. Test that a LIVE order and its audit rows survive a reset.
4.4 Action state machine and execution protocol
- States: PENDING -> APPROVED -> EXECUTING -> EXECUTED | FAILED | UNKNOWN; PENDING -> REJECTED; FAILED -> APPROVED only by an explicit human Retry; UNKNOWN leaves that state only through Reconcile (a direct retry from UNKNOWN returns 409).
- Fixed allowlist of action types (else 422). Execute on a non-APPROVED action returns 409. Execute on an EXECUTED action returns 200 with already_executed=true and no side effect. Re-approve is a 200 no-op; approving an EXECUTED action is 409.
- Atomic claim: one conditional update SET status='EXECUTING', claim_token=<uuid>, claimed_at=<utc> WHERE id=? AND status='APPROVED'. Only the caller whose update changes exactly one row proceeds; every other caller returns the current state and makes NO external call. The local change and any external call use a stable idempotency key derived from the action id (for PayPal send PayPal-Request-Id only on endpoints whose official docs confirm support; do not assume add-tracking does). Only after CONFIRMED success commit EXECUTED + executed_at + before/after diff + result + audit row in ONE local transaction. Never set EXECUTED before the external call succeeds.
- FAILED = known NOT to have succeeded: local validation failed before sending; connection could not be established so nothing was transmitted (DNS failure, connection refused, connect timeout); or a PayPal 4xx rejecting the request (including 429). Store a sanitized error. Retry reuses the same idempotency key.
- UNKNOWN = may have succeeded: read timeout after sending, connection reset/closed mid-response, any 5xx, a crash after sending, or an EXECUTING claim older than 5 minutes. Never auto-retry; stale-claim recovery may mark UNKNOWN but never re-executes.
- EXECUTED = success confirmed and local result + audit committed.
- Reconcile returns exactly ONE outcome: APPLIED (external effect verified, e.g. read-back shows the tracking number; mark EXECUTED with sanitized evidence + audit row); NOT_APPLIED (the system positively shows the effect is absent; only then may the action return to APPROVED, and only with explicit human confirmation such as {"confirm_not_applied": true}, else 409; audit who confirmed and the evidence); INDETERMINATE (cannot be established; stays UNKNOWN, no retry, UI says "outcome not confirmed"). "Could not find it" is INDETERMINATE, never NOT_APPLIED.
- Guarantee to state: the local claim/transition is protected against concurrent duplicate execution; external calls are protected by an idempotency key only where the endpoint supports one. Document the residual duplicate-call risk in README Limitations.
- Required tests: 8 concurrent executes -> one claim, one mock external-call attempt, one audit row; execute before approval 409; allowlist violation 422; 4xx and connect failure -> FAILED; read timeout, 5xx, connection reset, crash simulation and stale claim -> UNKNOWN; retry reuses the same idempotency key; direct retry from UNKNOWN 409; APPLIED -> EXECUTED with evidence; NOT_APPLIED without confirmation 409; with confirmation -> APPROVED + audit row; a read error -> INDETERMINATE; approve/re-approve rules; the agent cannot claim or execute.
4.5 UI and operations
Execute is disabled unless APPROVED. Risk reasons are visible at 1280 px without horizontal scrolling; layouts become cards at 390 px. Good contrast, accessible labels and focus states, loading/empty/error states, no unexpected console errors.

## 7. Mutation testing (phase-aware)
scripts/mutation_check.py holds a registry: id, since_phase, file, exact old text, new text, targeted tests. It takes --phase N (CI passes the PHASE file contents). For each mutation with since_phase <= N it copies the repo to a temp directory (NEVER the working tree), applies the mutation, runs the targeted tests, asserts at least one fails, and deletes the copy. If an applicable mutation's target text is missing it FAILS; later-phase mutations are listed as "not yet applicable". It writes MUTATION_REPORT.md (mutation, failing tests, raw output) and exits non-zero if any applicable mutation is not caught. CI runs it.
Registry: Phase 0: (1) seeding ignores DEMO_MODE; (2) naive timestamps instead of UTC Z; (3) the order-404 branch removed. Phase 1: demo reset also deletes LIVE rows. Phase 2: remove the 409 check; non-atomic claim (read then write); remove the allowlist; set EXECUTED before the external call; classify read timeout as FAILED; classify 5xx as FAILED; allow NOT_APPLIED without the confirm flag; map INDETERMINATE to NOT_APPLIED. Phase 5: secrets written to logs; token cache never expires. Phase 6: hallucination guard removed; the agent allowed to execute a write tool.
